این یکی هنوز موضوع قطعی پایان‌نامه‌ام نیست. پروپوزالم هم هنوز تأیید نشده و احتمالاً خیلی چیزها تا نسخه‌ی نهایی تغییر می‌کنن، ولی این چند روز یک ایده بیشتر از بقیه توی ذهنم مونده و گفتم قبل از اینکه وسط فایل‌ها و مقاله‌ها گم بشه، همینجا ثبتش کنم.

ایده به شکل خیلی ساده اینه:

**اگر یک LLM در یکی از مراحل Code Review اشتباه کنه، این اشتباه چقدر روی تصمیم‌ها و خروجی‌های بعدی اثر می‌ذاره؟**

و سؤال بعدی که شاید جالب‌تر باشه:

**اگر بفهمیم کدوم مرحله بیشتر باعث خراب شدن ادامه‌ی مسیر می‌شه، آیا می‌تونیم فقط همون‌جا مدل رو وادار کنیم جواب خودش رو دوباره بررسی کنه؟**

## اصلاً چرا چندمرحله‌ای؟

یکی از مقاله‌هایی که فعلاً دارم ازش شروع می‌کنم، [E4R-Reviewer](https://doi.org/10.1145/3832096) ـه.

ایده‌ی E4R اینه که Automated Code Review رو فقط به شکل «یه تکه کد بده، یه review comment بگیر» نبینه و فرآیند review رو به چند مرحله‌ی مشخص تقسیم کنه:

`Quality Estimation → Issue Localization → Issue Classification → Issue Description → Fix Suggestion → Code Refinement`

یعنی مدل اول باید بفهمه اصلاً مشکلی وجود داره یا نه، بعد محلش رو پیدا کنه، نوع مشکل رو تشخیص بده، توضیحش بده، راه‌حل پیشنهاد کنه و در نهایت به کد اصلاح‌شده برسه.

خود E4R این ساختار چندمرحله‌ای رو برای Automated Code Review استفاده می‌کنه و کد، داده و بخش‌های مربوط به آموزش و inference اون هم در [Replication Package](https://doi.org/10.5281/zenodo.18417185) منتشر شده.

چیزی که برای من جالبه اینه که وقتی این مراحل رو از هم جدا می‌کنیم، یه سؤال جدید به وجود میاد:

**اگر وسط یکی از این زنجیره اشتباه بشه، بقیه‌شون چی می‌شن؟**

مثلاً فرض کنیم مدل درست فهمیده که یک issue وجود داره، ولی محلش رو اشتباه پیدا کرده.

ممکنه بعدش:

- نوع مشکل رو هم اشتباه تشخیص بده،
- توضیح اشتباهی درباره‌ی علتش بسازه،
- برای یک مشکل اشتباه fix پیشنهاد بده،
- و در آخر کدی تولید کنه که اصلاً مشکل اصلی رو حل نکرده.

این چیزیه که فعلاً با عنوان **Error Propagation** دارم بهش فکر می‌کنم.

البته نمی‌خوام از قبل فرض کنم چنین propagationای حتماً وجود داره. خود وجود و شدت این رابطه باید چیزی باشه که آزمایش بشه، نه چیزی که از اول درست فرضش کنیم.

## اولین چیزی که دلم می‌خواد بفهمم

فرض کنیم برای هر نمونه بتونیم وضعیت مرحله‌ها رو چیزی شبیه این ثبت کنیم:

```text
Localization      Correct
Classification    Error
Description       Error
Fix Suggestion    Error
Code Refinement   Error
```

اگر این کار رو برای تعداد زیادی نمونه انجام بدیم، می‌شه سؤال‌هایی مثل این پرسید:

وقتی `Localization` غلط بوده، چند درصد مواقع `Fix Suggestion` هم غلط شده؟

بعد می‌شه این رو با حالتی مقایسه کرد که Localization درست بوده.

اگر اختلاف قابل توجهی وجود داشته باشه، حداقل یک نشونه داریم که خطای اون مرحله با خراب شدن مراحل بعدی ارتباط داره.

ولی این هنوز جواب کامل نیست.

چون **همبستگی بین دو خطا لزوماً به این معنی نیست که خطای اول باعث خطای دوم شده.**

و دقیقاً اینجاست که قسمت جالب‌تر ماجرا شروع می‌شه.

## اگر موقتاً یک مرحله رو درست کنیم چی؟

ایده‌ای که فعلاً دارم چیزی شبیه **Oracle Intervention** ـه.

فرض کنیم مدل Localization رو اشتباه انجام داده.

در یک آزمایش، به‌جای خروجی اشتباه مدل، موقتاً Localization درست رو از Ground Truth وارد pipeline می‌کنیم و مراحل بعدی رو دوباره اجرا می‌کنیم.

اگر بعد از این کار Description، Fix یا Code Refinement به‌طور محسوسی بهتر بشن، اون‌وقت دلیل قوی‌تری داریم که بگیم:

> شاید Localization واقعاً یکی از نقاط مهم این زنجیره باشه.

ولی اگر Localization رو کاملاً درست کنیم و خروجی‌های بعدی تقریباً هیچ تغییری نکنن، احتمالاً مشکل اصلی جای دیگه‌ایه.

این قسمت مهمه چون قبل از اینکه کلی verifier و prompt و مدل اضافه کنیم، کمک می‌کنه اول بفهمیم **اصلاً کجا ارزش مداخله کردن داره.**

یعنی به‌جای اینکه روی همه‌ی stageها verification بذاریم، شاید فقط یک یا دو مرحله واقعاً مهم باشن.

## بعدش Self-Verification وارد می‌شه

مشکل Oracle مشخصه: توی دنیای واقعی Ground Truth نداریم که هر بار جواب اشتباه مدل رو با جواب درست عوض کنیم.

پس اگر بفهمیم مثلاً Localization یا Classification مرحله‌ی حساسی بوده، سؤال بعدی می‌شه:

**آیا خود مدل، یا یک verifier جدا، می‌تونه قبل از ادامه‌ی pipeline خروجی اون مرحله رو بررسی کنه؟**

چیزی که فعلاً توی ذهنم دارم خیلی پیچیده نیست.

Verifier می‌تونه خروجی یک stage رو همراه با Code Diff و شواهد موجود بگیره و یکی از این حالت‌ها رو برگردونه:

```text
ACCEPT
REVISE
UNCERTAIN
```

اگر `ACCEPT` بود، pipeline ادامه پیدا کنه.

اگر `REVISE` بود، همون مرحله یک بار دیگه تولید بشه.

و اگر `UNCERTAIN` بود، بسته به طراحی آزمایش باید تصمیم گرفت که خروجی فعلی نگه داشته بشه یا مسیر دیگه‌ای طی بشه.

خود Self-Verification هم البته مسئله‌ی حل‌شده‌ای نیست. این‌طور نیست که چون یک مدل می‌تونه جواب تولید کنه، الزاماً در تشخیص درست یا غلط بودن جواب خودش هم به همون اندازه خوب باشه.

برای همین فعلاً Self-Verification رو بیشتر به چشم **یک سؤال آزمایشی** می‌بینم تا یک راه‌حل از قبل برنده.

یکی از کارهایی که در این زمینه جالبه، مقاله‌ی [Learning to Self-Verify Makes Language Models Better Reasoners](https://proceedings.mlr.press/v306/chen26es.html) عه که مشخصاً روی توانایی self-verification در مدل‌های زبانی کار می‌کنه.

## یه نکته‌ی مهم دیگه: هزینه

یه دام ساده هم این وسط وجود داره.

فرض کنیم نسخه‌ای که Self-Verification داره بهتر شد، ولی برای هر نمونه چند بار بیشتر مدل رو صدا زدیم.

اون‌وقت معلوم نیست بهبود به خاطر verification بوده یا فقط به خاطر این بوده که compute بیشتری خرج کردیم.

برای همین یکی از مقایسه‌هایی که فعلاً منطقی به نظر می‌رسه **Compute-Matched Retry** ـه.

یعنی تقریباً همون هزینه‌ی اضافه‌ای که برای verification مصرف شده رو به یک baseline ساده بدیم که فقط دوباره تلاش می‌کنه.

بعد مقایسه کنیم:

`Self-Verification vs. Simple Retry`

اگر با هزینه‌ی تقریباً مشابه، Self-Verification خروجی بهتری بده، اون‌وقت شاید جالب‌تر بشه.

اگر نه، شاید کل ماجرا فقط این بوده که مدل فرصت بیشتری برای جواب دادن داشته.

## دیتاست هم خودش یه داستانه

یکی از چیزهایی که فعلاً هنوز کامل قفل نشده، دیتاست و baseline نهایی کاره.

E4R یک [Replication Package](https://doi.org/10.5281/zenodo.18417185) منتشر کرده و داده و کدهای مربوط به آموزش و inference در دسترس هستن، که طبیعتاً گزینه‌ی خوبی برای شروعه.

یه کار مرتبط دیگه هم [Carllm](https://doi.org/10.1145/3695993) ـه.

Carllm هم روی Automated Code Review کار می‌کنه و review رو به بخش‌هایی مثل تشخیص مشکل، پیدا کردن موقعیت مشکل، توضیح و پیشنهاد repair می‌شکنه.

این نوع datasetها برای چیزی که من دنبالش هستم خوبن، چون اگر بخوام Error Propagation رو بررسی کنم، نیاز دارم بدونم در هر stage «جواب درست» چی بوده.

مثلاً برای `Issue Classification` قضیه نسبتاً روشنه: category مدل رو با Ground Truth مقایسه می‌کنیم.

ولی برای `Issue Description` یا `Fix Suggestion` دیگه Exact Match جواب نمی‌ده.

ممکنه Ground Truth بگه:

> قبل از dereference باید بررسی شود که x مقدار null ندارد.

و مدل بگه:

> مطمئن شوید x قبل از دسترسی به فیلدهایش non-null است.

جمله‌ها یکی نیستن، ولی از نظر معنایی تقریباً یک چیز رو می‌گن.

پس برای بعضی stageها احتمالاً باید rubric مشخص، evaluator مستقل یا ترکیبی از ارزیابی ماشینی و انسانی وجود داشته باشه.

و این خودش یکی از بخش‌هایی هست که هنوز باید خیلی دقیق‌تر بهش فکر کنم.

## چیزی که فعلاً می‌خوام از این ایده دربیاد

اگر این مسیر واقعاً تبدیل به پایان‌نامه بشه، چیزی که دوست دارم آخرش بفهمم تقریباً این‌هاست:

1. **خطاها در یک Code Review چندمرحله‌ای کجا ایجاد می‌شن و چطور به مراحل بعدی می‌رسن؟**
2. **کدوم stageها واقعاً نقاط مهمی برای مداخله هستن؟**
3. **اگر یک stage مهم رو درست کنیم، downstream واقعاً بهتر می‌شه یا نه؟**
4. **آیا Self-Verification می‌تونه بخشی از cascading error رو کم کنه؟**
5. **و اگر می‌تونه، آیا ارزش هزینه‌ی اضافه‌ای که ایجاد می‌کنه رو داره؟**

فعلاً کلی چیز هنوز بازه.

Baseline نهایی معلوم نیست.

Dataset هنوز باید دقیق‌تر بررسی بشه.

مدلی که قراره reviewer یا verifier باشه قطعی نیست.

و خب، خود پروپوزال هم هنوز تأیید نشده. :))

برای همین فعلاً بیشتر از اینکه بخوام بگم «موضوع پایان‌نامه‌ام اینه»، ترجیح می‌دم بگم:

**این یکی از مسیرهاییه که فعلاً ارزش دنبال کردن داره.**

شاید چند هفته‌ی دیگه بخشی از ایده عوض بشه، شاید ساده‌ترش کنم، شاید اصلاً مسیر دیگه‌ای جذاب‌تر بشه.

ولی فعلاً سؤال‌هاش برام جالبه و احتمالاً برای این مرحله، همین کافیه.
